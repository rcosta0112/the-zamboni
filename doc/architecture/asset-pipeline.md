## Export (proposed)

1. **Blender → glTF (`.glb`)**, one file per area (ship interior, ship exterior, each landing site) and one per reusable prop or character. Export with **Custom Properties** on so the naming contract below reaches the game as glTF `extras`.
2. **Optimise** with [glTF-Transform](https://gltf-transform.dev/): Meshopt or Draco geometry compression, KTX2 textures, deduplication. A script in the repo runs this so it's repeatable.
3. **Output** to the version's `public/`, which is committed.

**Units and orientation:** metres, scale applied, Blender's default glTF export (+Y up). **The ship file is the game 1:1** (owner, 2026-10-19): 1 Blender unit = 1 m, and the player's Dr. Green stands **1.23 tall at armature scale 1**. No export applies a correction factor; every export stops (a `SCALE:` line) if her armature isn't at scale 1 or her height is off by more than 0.01 ([`app/prototypes/0.0.2/tools/scale_check.py`](../../app/prototypes/0.0.2/tools/scale_check.py)). Anything animated on her in the file fits the game as made. (Until 2026-10-19 the game scaled the ship by 1.4856 and the exports resized her and the crew: [`app/prototypes/0.0.2/tools/normalize-scale.py`](../../app/prototypes/0.0.2/tools/normalize-scale.py) put that into the file, as 1.21.)

### The gate (2026-10-20, item 48)

**An export replaces the game's files only when nothing differs** from the last export that was taken (owner, 2026-10-20: "anything that looks odd and could potentially give an unexpected result should stop the export. Let's start broad and add exceptions as we go"). [`export.mjs`](../../app/prototypes/0.0.2/tools/export.mjs) writes the new files to `app/prototypes/0.0.2/.export/<what>/out/` and compares them with the game's (compare-glb: objects, triangles, bounds, materials, tags, animations; then the bytes) and its lines with the last taken export's. **What stops it:** any difference in the files; a new `PERF:`, `NODES:`, `NOTE:` or `POSE:` line; any `STOP:` line. Then the summary lists every reason (`STOPPED: …`), the game's files are left alone, and **`npm run export:accept -- <ship|crew|player>`** takes the waiting files as they are, without running Blender again; it refuses if the `.blend` was saved after that export. After a taken export that changed something, the **after-export check** runs if the dev server is up ([`after-export.js`](../../app/prototypes/0.0.2/tools/after-export.js), about 30 s: the doors, the collider against the drawn hull, the crew, the ladder's foot, a walk from the cargo bay into engineering); otherwise the summary gives its command.

**The exceptions** (each a rule in `EXCEPTIONS` in `export.mjs`; flagged with `FLAG:` lines, they don't stop the export):

| Since | Exception | Why |
|---|---|---|
| 2026-10-20 | The `POSE:` line for the frame the file was left on | Every export runs at the start frame: the frame doesn't change the export (owner) |
| 2026-10-20 | A new id, or an id whose object was renamed or moved to another collection (an id gone, or changing kind, stops it; two objects with one id stop it; something the game uses without an id is a `NOTE:`) | Ids are what scenes, Ink and cutscenes name: only losing one breaks them (the game's structure, pass 1) |
| 2026-10-20 | The crew's places, poses and actions (objects moved, an animation changed, a `CREW:` line changed) | The crew will be in different places and animations in different scenes (owner) |

**The crew's checks** (`export-ship-crew.py`, owner 2026-10-20): a `CREW:` line per character (hips, facing, action). **These stop the export (`STOP:`):** an animated character with no action; one that had an action in the last taken export and has none; one missing since then; one at the world origin, outside the hull's bounds (`Hull_Merged`), below the lower deck or reaching more than 0.05 below the floor of their deck (`Floor Bottom`, `Floor Top.001`); two whose hips are closer than 0.3 m. **The player export** stops if a part listed for her or the ladder clip (`--clip`, `--clip-start`) is missing.

**Backface culling on.** Double-sided materials cost performance (every hidden back face is drawn too). Thin parts that need a back get real geometry in Blender; the export reports any double-sided material (owner, 2026-10-08).

**Lighting:** interiors get baked lighting (Cycles bake to lightmaps on a second UV set), since the web renderer has no real-time global illumination. The baking workflow is to be worked out in the vertical slice.

**Characters:** source file `models/The Crew 1.09 Dr. Green.blend`. One shared skeleton for the humans, their outfits and Adam; mitten hands. Each human has at least two outfits (indoor jumpsuit with a name tag, outdoor parka), each its own mesh and texture. Adam is a single rigid-block mesh; both bodies share one animation set. Details and file split: [game architecture plan: characters](../plans/architecture/game-architecture/characters.md); they move here once confirmed.

**Ruins:** mostly unique models per landing site (owner, 2026-10-08).

**Collision:** simplified `*_col` meshes, boxes or heightfields, exported with the model they belong to and counted in its download budget.

## The ship's reference file

**`resources/models/The Zamboni 1.21.blend` is the reference for the ship** (since 2026-10-19; 1.19 from 2026-10-12, owner): the scene as it is in the game. 1.19 was built once from 1.18 by [`app/prototypes/0.0.2/tools/build-ship-reference.py`](../../app/prototypes/0.0.2/tools/build-ship-reference.py); the owner made 1.20 from it; 1.21 is 1.20 at the game's scale ([`normalize-scale.py`](../../app/prototypes/0.0.2/tools/normalize-scale.py), 1.20 untouched). It's edited in Blender from here on. **What's exported is a list**, [`app/prototypes/0.0.2/tools/ship-export-list.json`](../../app/prototypes/0.0.2/tools/ship-export-list.json) (owner, 2026-10-19: the owner switches collections on and off while working, so that's no longer the criterion): the parts, the props (with the group each is merged into and its `seeThrough`), the collision pieces and the light markers, made from what the game had (1.19's export) by [`ship-export-list.py`](../../app/prototypes/0.0.2/tools/ship-export-list.py). To add something to the game or take it out, edit the list; the export prints a `NOTE:` for what's listed but not in the file, and for what's in the file and not listed. **How** each thing behaves still comes from custom properties in the file (the naming contract below).

**Each version exports from its own file** (2026-10-20, item 51; [decision log](../decision-log.md)). The current version (0.0.2) exports from the working file above, into its own `public/`. A frozen version exports from **its archive**, `resources/archive/<version>/`: the `.blend` as it was at the freeze, its images and font packed in, so later edits to the working file or its textures can't reach it. 0.0.1's is `resources/archive/0.0.1/The Zamboni 1.21 (0.0.1).blend` (21 MB; made by `pack_archive.py` beside it, with a `README.md`); its ship, collider and crew export byte-identical to 0.0.1's game files (the player's export isn't deterministic, from either file). The node library's path is stored absolute (Blender 5.2's install).

What the file has that 1.18 didn't:

- **Doors closed.** The fridge, the cupboard and the trapdoor were modelled open; the cargo ramp was held open by one keyframe (removed, with its action). The game takes the file's pose as "closed".
- **The objects removed from the game are deleted** (the oscilloscope and its cable, the battery charger and its batteries, the rungs on the cockpit bulkhead).
- **Tags on objects and collections** (below).
- **Collection `Game`:** `Game Lights` (the room light markers, empties) and `Game Collision` (the `*_col` objects: three pieces per bulkhead, a box under the hull, a box under each front thruster; drawn as wireframes, not rendered). The `Game` collection can be excluded from the view layer to keep it out of the way: the export includes it anyway. Move, resize or add `*_col` objects freely: every mesh whose name ends in `_col` is joined into the collider, whatever collection it's in. To replace an object's automatic collision with your own, add a `*_col` mesh and tag the object `collider: "none"` (works on parts and on props).
- **Backface culling on** for the 57 materials the ship's export uses (44 were double-sided). Not the crew's own materials.

What stays in the export script, because it's derived from the scene: applying modifiers, baking and merging props, baking a part posed by an armature, joining the collider, hinge points and door axes, the `PERF:` report.

**Checking an export change:** `node tools/compare-glb.mjs <before.glb> <after.glb>` (in `app/prototypes/0.0.2/`) lists every object whose triangles, bounds, materials or custom properties differ. Used on 2026-10-12 to prove the reference: exported with the new script, it differed from 1.18's export only in the ramp (closed) and the new `opensWith` tag; the collider had the same vertices and area (21 of 48,004 triangles fewer, from the order pieces are merged in).

## Naming contract (proposed)

> **[Agent note]** **Update 2026-10-20 (the game's structure, pass 0b):** the names the game uses follow the approved table in [ship-names.md](../plans/architecture/game-architecture/ship-names.md), in plain words with spaces (`Side Door`, `Cockpit Door Panel Front`, `Jetpack 1`), not the lowercase prefixes below. **A mesh takes its object's name plus ` Mesh`** (`Side Door Mesh`); a mesh shared by several objects takes their kind's (`Bulkhead Door Right Mesh`, `Door Panel Mesh`). The suffix keeps a mesh's name from ever taking an object's in the game (GLTFLoader gives the second user of a name `_1`).

Objects are recognised by **name prefix** and configured with **custom properties**. Names are lowercase with underscores in Blender; ids in data files match them.

| Prefix / property | Meaning | Example |
|---|---|---|
| `id`, `kind` | **Since 2026-10-20 (the game's structure, pass 1):** the stable id the game, scenes, Ink and cutscenes name it by (lowercase words joined by hyphens, written once from the name, kept when the object is renamed), and what it is (a kind defined in the game, `src/kinds.ts`). On the 33 objects the game uses; static scenery has none. The export prints an `ID:` line for each and writes [`ids.json`](../../app/prototypes/0.0.2/tools/ids.json) when it's taken (id, kind, name, collection). Behaviour comes from the kind; the `door…` tags below still give the instance (axis, angle, slide) and, until pass 6, a copy of the behaviour (the game warns if it disagrees with the kind) | `id: "cockpit-door-left"`, `kind: "sliding-door"` |
| `door_*` | A door | `door_galley`, `door_hatch_cargo` |
| `interact: <verb>` | What the player can do: `pickup`, `use`, `open`, `talk`, `scan`, `sit`. **No longer read by the game** (2026-10-20: it goes by `kind`); the export still keeps a tagged prop an object of its own | `interact: pickup` |
| `device: <type>` | Device behaviour class. **No longer read by the game** (2026-10-20): it finds devices by `kind` | `device: boombox`, `device: lever` |
| `requires: <id>` | Dependency on another object or story flag | `requires: lever_01` |
| `controls: "<id>"` | A device that opens/closes another object, named by its **id** (since 2026-10-20; it was the object's name). In use: the cargo-hold keypads, the bulkhead doors' panels, the window's lever: [`features/interaction.md`](../features/interaction.md). A child of the device that's tagged as a door is its handle and moves with it (the lever). The game finds the devices by kind (`keypad`, `door-panel`, `lever`); an id that doesn't exist stops the export | `controls: "cargo-ramp"` |
| `part: true` | In the ship file: a fixed part of the ship, exported as its own object and colliding with its real shape. Everything else render-visible in the ship's collections is a prop. Read by the export only | hull, floors, bunks, seats, doors, keypads |
| `doorAxis`, `doorAngle`, `doorToGround`, `doorStartOpen` | In the ship file: a door. The object's own rotation axis (`"X"`, `"Y"`, `"Z"`), the open angle in degrees, opens until it touches the ground, starts open in the game. **Closed in the file.** The export writes them as one property, `door` | `doorAxis: "Z"`, `doorAngle: 100` |
| `door: {axis, angle, toGround, startOpen}` | In the exported file (written by the export from the four above): hinge axis (glTF axes, ship space), open angle (radians). In use: [`features/interaction.md`](../features/interaction.md) | the side door, hatches, fridge and lockers |
| `doorSlide`, `doorDistance`, `doorAuto` | In the ship file: a **sliding** door. The object's own axis it slides along (`"X"`, `"Y"`, `"Z"`), how far it slides to open (Blender units; the sign gives the direction), and whether it opens when she's near. **Closed in the file.** The export writes them as `door: {slide, auto}` (the slide as one vector, glTF axes, ship space) | the bulkhead doors' leaves, `Lab Window`, the lever `Level` |
| `opensWith: "<id>"` | A door that opens and closes together with another, named by its **id** (since 2026-10-20): one target, and a device that controls one moves both. An id that doesn't exist stops the export | `top-hatch-upper` ↔ `top-hatch-lower`; `cockpit-door-right` ↔ `cockpit-door-left` |
| `moving: true` | In the ship file: moves, but not as a door (the game drives it itself). Like a door, its hinge is recorded and it's left out of the ship's collider. Read by the export only | `Door Cargo` |
| `collider: "hull"` / `"none"` | In the ship file: this part collides as its convex hull (dense furniture) / doesn't collide (its `*_col` pieces do, or nothing does). Without it, a part collides with its real shape. Read by the export only | `Contraption`; the bulkheads, the sliding doors |
| `export: false` | In the ship file, on an object or a **collection**: never exported as a prop | the unmerged `Hull`; the `Crew` collections |
| `hinge: [x, y, z]` | A moving part's hinge point (glTF axes, set by the export). **Not `pivot`:** three r186's GLTFLoader consumes a `pivot` extra on a node with children | `Door Cargo`, every door |
| `scan_id: <id>` | Entry this object adds to the scanner database | `scan_id: ruin_gate_01` |
| `structure: true` | The see-through hull's structure group: always cut by the hole (untagged = furniture, cut only while it hides her). [`features/see-through-hull.md`](../features/see-through-hull.md) | hull, walls, ceilings, floors, doors, hatches |
| `seeThrough: "keep"` | See-through exception: furniture never cut for hiding her (its shape lets her show through) | `3d Printer` |
| `seeThrough: "solid"` | See-through exception: never cut on her deck, not even near the camera. On a **collection**: every prop in it | cockpit furniture, `Contraption`, `Sledge`; the `Cockpit` collection |
| `divider: true` | See-through: an interior divider, solid while the camera is inside the ship (unless it hides her); from outside, the hole or cut as a whole | bulkheads, inner walls |
| `prop: true` | A prop (set by the export): doesn't cast shadows in the game | merged props, crates, chests |
| `lightRoom`, `lightColor`, `lightEnergy` on an empty | In the ship file: a room light marker (glTF can't carry area lights). The export writes them as one property, `light: {room, color, energy}`; the game builds point lights from it | `light cargo bay (Area.002)` |
| `character: "<name>"` | Part of a placed character (the crew file) | Dr. Kaufman |
| `cuttable: false` | Never cut by the see-through hull; everything else in the ship is (in use: [`features/see-through-hull.md`](../features/see-through-hull.md)). Until 2026-10-08 the contract was the reverse, `cuttable: true` on what may be cut | landing gear |
| `*_col` | Invisible collision mesh for its parent (simplified geometry). In the ship file: joined into the ship's collider | `Bulkhead Cargo Left_col`, `Hull Underside_col` |
| `reach: "through"` on a `*_col` | In the ship file: a collision box she can't walk through but can reach past (the reach test ignores it). Must be convex. Exported as an object of its own in the collider file | `Box Crew Galley_col` |
| `zone_indoor_*`, `zone_outdoor_*` | Trigger volumes that switch indoor/outdoor rules | `zone_indoor_cockpit` |
| `boundary_soft`, `boundary_hard` | Outdoor boundary volumes | |
| `spawn_*` | Player and NPC spawn points | `spawn_player_copilot_seat` |
| `mass: <kg>` | Physics mass for pickable objects | `mass: 0.3` |
